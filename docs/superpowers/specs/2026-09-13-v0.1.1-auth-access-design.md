# CodeLift AI v0.1.1 Self-Service Account Access Design

## Status and approval boundary

This document is the proposed design for CodeLift AI v0.1.1. It is the
required approval gate for an architectural change that adds transactional
email and a second authentication method. No production implementation,
provider account mutation, DNS change, secret creation, live email, database
mutation, deployment, tag, or release publication is authorized by this
document.

Implementation may begin only after the operator approves this design. A
separate implementation plan will then translate the approved design into
test-first, reviewable commits. Real provider setup and the first live email
remain behind the later `EMAIL_PROVIDER_OPERATOR_SETUP_REQUIRED` gate.

The product name is **CodeLift AI**. The repository/project is **CodePilot** at
`muckele/CodePilot`. The current public release tag `v0.1.0-mvp` remains an
immutable release artifact.

## Release objective

The release makes account access self-service without removing password
authentication. It delivers exactly four user-facing changes:

1. an obvious **Sign out** control available throughout the private workspace;
2. the existing email-and-password login, preserved as the primary form;
3. an optional emailed six-digit sign-in code that creates the same normal
   authenticated session as password login; and
4. self-service password-reset email requests that reuse the released reset
   token, fragment URL, completion, and session-revocation flow.

The release does not add SMS, phone data, passwordless-only accounts, social
login, OAuth, passkeys, MFA enrollment, registration changes, billing, roles,
user administration, learning features, or a broad UI redesign. The existing
operator invitation and reset CLI remains available and independent of the
email provider.

## Existing architecture to preserve

The released system already has the right security boundary:

```text
Browser
  -> HTTPS Funnel / loopback-published Nginx web ingress
     -> private Node/Express API
        -> authenticated transaction-capable MongoDB replica set
```

The browser calls only the Node API. Node owns contract validation, exact
Origin checks, CSRF, authentication, session cookies, tenant scope, database
transactions, and provider calls. MongoDB is authoritative. The Python service
is unrelated to account access and remains optional.

The implementation must reuse these released controls:

- strict Zod request/response contracts;
- normalized lowercase email addresses;
- Argon2id passwords and dummy password verification for missing users;
- opaque session and CSRF tokens stored as SHA-256 digests;
- a secure `__Host-` HTTP-only, SameSite=Lax production cookie;
- exact configured Origin checks for mutations;
- replacement of the anonymous pre-auth session during login;
- Mongo transactions and the user `writeFence` for account/deletion races;
- one-hour, opaque, hashed password-reset tokens;
- transactional sibling reset revocation, one-time reset consumption, and
  all-session invalidation after reset;
- the `/reset-password#token=...` fragment flow, which keeps the bearer value
  out of HTTP request targets;
- explicit account-export sanitization and explicit transactional deletion;
- privacy-minimized normalized-route logs;
- encrypted database backup and isolated restore; and
- source-bound security, browser, container, and release-quality evidence.

The existing `POST /api/v1/auth/logout`, `logoutAccount(csrfToken)`,
`POST /api/v1/auth/reset-password`, `/reset-password`, and
`operator:access issue-reset` paths are retained. There is one logout endpoint
and one password-reset record model.

## Design options considered

### Option 1: synchronous provider boundary and purpose-specific login codes

Node creates a bounded auth credential transactionally, calls an injected
`TransactionalEmailProvider` after the transaction commits, and marks or
revokes the new credential according to the bounded provider result. Login
codes receive their own HMAC-protected collection. The web session state is
lifted into a narrow context so the application shell can perform logout.

This is the selected design. It has the smallest operational footprint,
preserves Mongo as the only product database, avoids a queue worker, and keeps
provider behavior testable without network access. Its known tradeoff is that
a provider timeout is an ambiguous delivery result; the affected credential is
revoked, so a delayed email may contain an unusable link or code. The user can
request another message or use operator recovery.

### Option 2: durable transactional-email outbox and worker

Node would persist jobs and a worker would deliver them with retries. This
improves delivery retry semantics but adds worker lifecycle, job leasing,
secret-bearing payload encryption, queue retention, dead-letter handling,
deployment topology, backup semantics, and another class of replay races.
That is disproportionate to a private pilot and conflicts with the focused
release scope. It is rejected for v0.1.1.

### Option 3: Resend calls in auth routes and an independent shell session

Routes could call Resend directly, while `AppShell` could independently fetch
CSRF/session data and clear browser state after logout. This is initially
shorter but couples the auth domain to one vendor and creates two competing
sources of client session truth. It makes provider tests, failure behavior,
and truthful logout harder to reason about. It is rejected.

## Selected component architecture

```text
Account UI / AppShell
  -> strict account API client
     -> account router: Origin + CSRF + endpoint rate limiter
        -> AccountService
           -> shared PasswordReset issuer -> PasswordReset
           -> email-code state machine -> EmailLoginCode
           -> existing session issuer -> Session
           -> bounded aggregate auth events -> PilotAggregate
           -> TransactionalEmailProvider
                -> Fake provider in tests (no network)
                -> Resend adapter in configured production
```

Authentication logic depends only on the internal provider interface. The
Resend adapter depends on configuration and native `fetch`; it is never
imported by browser code. No new runtime package or provider SDK is required.

## Transactional email provider

### Internal contract

`TransactionalEmailProvider` has only two operations:

```ts
interface TransactionalEmailProvider {
  sendPasswordReset(input: {
    to: string;
    resetUrl: string;
    expiresAt: Date;
    idempotencyKey: string;
  }): Promise<void>;

  sendLoginCode(input: {
    to: string;
    code: string;
    expiresAt: Date;
    idempotencyKey: string;
  }): Promise<void>;
}
```

The interface returns no provider response body or provider message ID. It
either resolves or throws a bounded `TransactionalEmailError` whose reason is
one of `timeout`, `rejected`, `rate_limited`, `unauthorized`, or `unavailable`.
The public API never receives the provider error. The error carries no request
payload, recipient, key, code, token, reset URL, or raw response body.

### Resend adapter

The adapter uses native Node `fetch` to `POST https://api.resend.com/emails`
with `Authorization`, `Content-Type`, `User-Agent: codelift-api/0.1.1`, and an
`Idempotency-Key`. Resend documents HTTPS-only API access, bearer
authentication, and a required User-Agent for direct requests. The adapter
uses `AbortSignal.timeout` with the configured timeout, accepts only a 2xx
response, does not retain or log the response body, and performs no automatic
retry. One user request therefore causes at most one provider call.

The idempotency keys are secret-free and record-specific:

- `password-reset/<Mongo ObjectId>`
- `email-login-code/<Mongo ObjectId>`

Resend documents that email idempotency keys are retained for 24 hours and may
be up to 256 characters. The proposed values are well within that bound and do
not expose an email address or credential.

The sender passed to Resend is `CodeLift AI <validated EMAIL_FROM>`. Optional
`EMAIL_REPLY_TO` is sent only when configured. Open and click tracking are not
enabled for these transactional security messages. No attachment, provider
template, contact, audience, tag containing account data, or webhook is used.

### Email content

Both plain-text and minimal HTML bodies are rendered locally from fixed copy.
Dynamic values are contract-validated and HTML-escaped even though they are
server-generated.

Password reset email:

- subject: `Reset your CodeLift AI password`;
- explains that a password reset was requested;
- includes the existing one-time `/reset-password#token=...` URL;
- states that the link expires in one hour; and
- says that the recipient can ignore the email if they did not request it.

Login-code email:

- subject: `Your CodeLift AI sign-in code`;
- shows exactly one six-digit code;
- states that the code expires in ten minutes and is single-use; and
- says that the recipient can ignore the email if they did not request it.

There is no user-controlled display name, subject, HTML, or URL origin in a
message. The reset origin comes only from the validated server `WEB_ORIGIN`.

### Fake provider and E2E mailbox

The fake provider records structured calls in memory, can be configured by
tests to resolve or throw a bounded failure, and makes no network call. Unit
and Mongo integration tests inspect that in-memory mailbox directly.

Playwright runs the API in a separate process, so its fake provider uses an
optional test-only filesystem sink. `EMAIL_FAKE_OUTBOX_DIR` is accepted only
when `NODE_ENV=test` and `EMAIL_PROVIDER=fake`. It must be an absolute path
under the operating-system temporary directory. The reset helper creates the
directory with mode 0700; each atomic message file is mode 0600. Test helpers
consume a message by recipient and purpose without printing it. Global
teardown removes this exact test directory. It is outside the repository,
never mounted in production, never attached as Playwright evidence, and never
used for a real provider credential or real recipient.

## Configuration and secret contract

`ApiConfig` gains an `email` section with these exact settings:

| Input                          | Rule                                                                                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `EMAIL_PROVIDER`               | `disabled`, `fake`, or `resend`; defaults to `disabled` outside the v0.1.1 self-host profile; `fake` is rejected in production                               |
| `EMAIL_FROM`                   | Required for `resend`; one validated bare mailbox address, used as `CodeLift AI <address>`                                                                   |
| `EMAIL_REPLY_TO`               | Optional validated bare mailbox address; absence omits `reply_to`                                                                                            |
| `RESEND_API_KEY_FILE`          | Required for `resend`; absolute, readable, one ASCII line, 16–512 bytes, starts with `re_`, contains no whitespace; no direct secret environment alternative |
| `EMAIL_REQUEST_TIMEOUT_MS`     | Defaults to 5000; integer range 1000 through 10000                                                                                                           |
| `EMAIL_LOGIN_CODE_PEPPER_FILE` | Required for `resend`; absolute file containing a base64url encoding of exactly 32 random bytes                                                              |
| `EMAIL_FAKE_OUTBOX_DIR`        | Optional only for the test fake; rejected in development and production                                                                                      |

When the provider is `disabled`, the provider secrets and sender are not read,
`/api/v1/config` reports `emailSelfServiceEnabled: false`, password login and
operator reset remain available, and email request/verify endpoints return a
bounded capability-unavailable 503 without inspecting account existence. The
login page hides email self-service controls and retains the current support
path. A configured provider runtime failure does not flip this capability
flag; request endpoints keep their generic 202 contract.

When the provider is `resend`, production startup fails before readiness if
the sender, timeout, key file, or pepper file is invalid. Both secret inputs
are read using a generalized version of the existing bounded secret-file
loader. Direct `RESEND_API_KEY` and `EMAIL_LOGIN_CODE_PEPPER` values are not
supported, preventing accidental Compose literals.

The login-code constants are code-owned rather than operator-tunable:

- 6 numeric digits;
- 10-minute validity;
- 5 failed verification attempts;
- 60-second issuance cooldown; and
- 7-day post-expiry record retention through TTL cleanup.

This prevents an environment typo from silently weakening authentication.

## Production secret state and rotation

The self-host operator root gains exactly two API-only files:

```text
/Users/Matt/Library/Application Support/CodeLift AI Self-Host/
  secrets/
    resend-api-key
    email-login-code-pepper
```

The parent directories remain mode 0700; both files are regular,
non-symlinked, operator-owned, and mode 0600. Compose mounts them read-only
only into the API at `/run/secrets/resend-api-key` and
`/run/secrets/email-login-code-pepper`. Seed, web, MongoDB, backup helpers,
browser images, build contexts, and logs do not receive them.

An explicit self-host `email-configure` operation is added. It accepts a
validated sender, optional reply-to address, and the absolute path to an
operator-created mode-0600 Resend key file outside the repository. It refuses
a symlink, nonregular file, wrong owner, permissive mode, multiline value,
oversized value, or an already inconsistent email state. It copies the key
without displaying it, generates the independent 32-byte pepper with
`randomBytes`, writes both destination files atomically with mode 0600, and
updates only the non-secret email settings in protected `ops/compose.env`.
Existing Mongo and backup secrets are neither regenerated nor rewritten.

All self-host commands that can start or inspect the v0.1.1 API validate the
email files when `EMAIL_PROVIDER=resend`; a partial configuration fails before
Compose mutation. The v0.1.1 Compose definition requires `EMAIL_PROVIDER`,
`EMAIL_FROM`, and `EMAIL_REQUEST_TIMEOUT_MS`, passes only file paths for both
secrets, overrides the seed helper to `EMAIL_PROVIDER=disabled`, and preserves
the current volume name, loopback web binding, private API/Mongo ports,
read-only filesystems, resource limits, restart policy, and networks.

Key rotation is an operator operation with this order:

1. create a new sending-only, selected-domain Resend key and save it to a new
   external mode-0600 file without using chat or shell arguments;
2. run the bounded `email-rotate-key` operation, which stages a mode-0600 file,
   atomically replaces `resend-api-key`, retains the former key only as an
   API-unmounted mode-0600 rollback file, restarts only the API, and requires
   readiness;
3. perform the explicitly approved synthetic live-send check;
4. on success, run `email-finalize-key-rotation` to remove the rollback file,
   then revoke the old key in Resend; or
5. on failure, run `email-rollback-key`, restore API readiness, and revoke the
   unusable new provider key.

Pepper rotation intentionally invalidates every outstanding login code. The
bounded `email-rotate-pepper --invalidate-active-codes` operation first stops
the API, writes a new independently random 32-byte pepper atomically, deletes
only unconsumed `EmailLoginCode` records through an authenticated internal
operator command, starts the API, and verifies readiness. Passwords, sessions,
reset tokens, users, progress, the Mongo volume, and backups are not changed.
This operation is reserved for suspected pepper exposure and requires a fresh
encrypted backup and explicit operator approval.

| `POST /auth/password-reset/request` | `{ email }`                    | 202 with password-reset generic acknowledgement                | IP limit 429; disabled capability 503; configured-provider/account outcomes remain generic 202 |

The exact password-reset request body is:

```json
{
  "message": "If an account exists for that email, we sent a password-reset link."
}
```

The exact login-code request body is:

```json
{
  "message": "If an account exists for that email, we sent a sign-in code."
}
```

```text
That code is invalid or expired. Request a new code and try again.
```

Existing and nonexistent emails receive the same status, content type, strict
schema, and byte-equivalent JSON body for each request endpoint. No response
contains an email, account ID, invitation state, reset ID, code ID, cooldown
state, provider state, or last-login state.

Every new POST route performs the existing exact-Origin check and CSRF check
against the current pre-auth session before its service method. The email-code
success response uses the same cookie setter and auth-session response schema
as password login. No email address is placed in a public URL or query string.

`GET /api/v1/config` adds only `emailSelfServiceEnabled: boolean`; it does not
expose provider name, sender, reply-to, timeout, account state, or secret-file
paths.

## Password-reset request state machine

The released `issuePasswordReset` function remains the only reset issuer. Its
internal result becomes a non-public union that can represent `issued`,
`missing_account`, or `cooldown`; the operator CLI does not enable cooldown and
retains its current error and output behavior.

For a self-service request:

1. The router validates Origin, CSRF, body, and the password-reset-request IP
   bucket.
2. The service normalizes email through `emailAddressSchema` and records
   `password_reset_requested` without sensitive labels.
3. The shared issuer generates the existing 32-byte opaque token and digest.
   In one Mongo transaction it fences the matching user, enforces a 60-second
   account cooldown, revokes prior unused reset records, and creates exactly
   one new one-hour `PasswordReset` record with
   `createdBy: "self-service-email"`. A missing user creates no record.
4. Missing-account and cooldown outcomes skip the provider and proceed to the
   generic response.
5. For an issued record, the service builds the existing fragment reset URL
   from validated `WEB_ORIGIN` and sends exactly one email after the transaction
   commits.
6. Provider acceptance records `password_reset_email_sent`. A rejection or
   timeout conditionally revokes only the newly issued, still-unused record,
   records `password_reset_email_failed`, discards the raw token/link, and
   still returns the generic response. An ambiguous timeout may produce an
   unusable delayed email; it never leaves a valid unconfirmed credential.
7. The response is delayed to a 750 ms minimum public duration measured from
   handler entry. There is no random jitter. Strong IP limits and equivalent
   public content reduce practical enumeration, while the design explicitly
   does not claim perfect timing indistinguishability during provider slowness.

Reset completion remains unchanged: direct expiry validation, atomic
single-use consumption, Argon2id password replacement, sibling reset
revocation, deletion of every authenticated session for the user, and return
to login for authentication with the new password.

## Email login-code record

A new Mongoose model and `emaillogincodes` collection represent only the
email-code purpose:

| Field            | Type and rule                                                                      |
| ---------------- | ---------------------------------------------------------------------------------- |
| `_id`            | Mongo ObjectId generated before the digest                                         |
| `userId`         | Required indexed User ObjectId                                                     |
| `purpose`        | Required literal `email_login`                                                     |
| `codeDigest`     | Required 64-character hexadecimal HMAC-SHA-256 digest, `select: false`             |
| `expiresAt`      | Required creation time plus exactly 10 minutes                                     |
| `sentAt`         | Nullable date; verification requires it, preventing use before provider acceptance |
| `consumedAt`     | Nullable date; set exactly once on successful authentication                       |
| `revokedAt`      | Nullable date; set for replacement, attempt exhaustion, or delivery failure        |
| `failedAttempts` | Integer 0 through 5, initially 0                                                   |
| `createdAt`      | Mongoose creation timestamp                                                        |

No email address, plaintext code, raw session token, provider response,
provider message ID, email body, or email subject is stored in the record.

Indexes are:

1. `{ userId: 1, purpose: 1, createdAt: -1 }` for current-code, sibling,
   cooldown, deletion, and account-scoped lookup; and
2. `{ expiresAt: 1 }` with `expireAfterSeconds: 604800` for cleanup seven days
   after security expiry.

No partial unique index is used because issuance and provider completion are a
two-stage process. User fencing plus transactions serialize issuance. The TTL
monitor is only storage cleanup: request and verification filters always
enforce `expiresAt > now`, so security does not depend on prompt TTL deletion.

## Login-code cryptography

Production code generation uses `node:crypto` `randomInt(0, 1_000_000)` and
left-pads to exactly six decimal characters. `Math.random()` is prohibited.
Leading zeroes are retained.

The ObjectId is generated first. The digest is:

```text
HMAC-SHA-256(
  email-login-code pepper,
  "codelift:email-login:v1:" + recordIdHex + ":" + sixDigitCode
)
```

The production pepper is an independent 32-byte random secret from
`EMAIL_LOGIN_CODE_PEPPER_FILE`; Mongo, backup, AI, and provider credentials are
not reused. Verification recomputes a 32-byte digest and uses
`timingSafeEqual`. A fixed dummy record ID and a startup-computed dummy digest
exercise the same HMAC and constant-time comparison path when no user or valid
record exists. The code string is never converted to a number during parsing,
so leading zeroes survive.

Six digits are intentionally low entropy and are safe only in combination with
the server-side keyed digest, ten-minute expiry, single-use state, five-attempt
record lock, request cooldown, and IP limits. Database access without the
pepper is not enough to enumerate the code space offline.

## Login-code request state machine

1. The router validates Origin, CSRF, the strict `{ email }` body, and the
   login-code-request IP bucket.
2. The service normalizes email and records `email_login_code_requested` with
   no identifying labels.
3. For a matching user, one Mongo transaction increments the user write fence.
   If any unconsumed/unrevoked code was created in the preceding 60 seconds,
   the transaction returns `cooldown` without creating or sending. Otherwise
   it revokes every prior active email-login code and creates one pending
   record with `sentAt: null`, a ten-minute expiry, and the HMAC digest.
4. A concurrent request waits on the same user write fence; after retry it sees
   the pending recent record and receives the generic cooldown outcome. Only
   one provider call occurs.
5. The provider is called only for a real user and new record. Provider
   acceptance conditionally sets `sentAt` if the record is still active and
   records `email_login_code_email_sent`. Provider rejection or timeout
   conditionally revokes the record and records
   `email_login_code_email_failed`. If account deletion or replacement won the
   race, the emailed code remains unusable.
6. Missing user, cooldown, send success, send failure, and state-race outcomes
   all return the exact generic 202 response after the 750 ms minimum public
   duration. A missing user performs code generation, dummy HMAC, and bounded
   database work but no provider call.

The provider call is deliberately outside a Mongo transaction, so an external
timeout cannot hold database locks. No automatic retry can create duplicate
messages. A new request after a revoked delivery failure may issue immediately;
a successfully accepted code enforces the full 60-second cooldown.

## Login-code verification state machine

1. The router validates Origin, CSRF, the strict normalized email plus
   `/^\d{6}$/` code, and the verification IP bucket.
2. The service selects the newest record for that user/purpose whose
   `sentAt` is non-null, `expiresAt` is in the future, `consumedAt` and
   `revokedAt` are null, and `failedAttempts < 5`, explicitly selecting its
   hidden digest. A missing or invalid state performs the dummy comparison and
   returns the generic 401.
3. The code digest comparison is constant-time. A mismatch runs a transaction
   that conditionally increments the same active record. Mongo transaction
   conflict retry makes concurrent wrong attempts serial. The transition from
   attempt 4 to 5 also sets `revokedAt` in that transaction. Every outward
   mismatch is the same generic 401 and records `email_login_code_failed`.
4. A matching digest runs a transaction that refetches and conditionally claims
   the still-valid record, increments the user write fence, sets
   `consumedAt`, revokes sibling active login codes, deletes the supplied
   pre-auth session, and calls the existing session issuer for the user.
5. The returned cookie, CSRF token, idle/absolute expiry, user activity, and
   response schema are exactly those of password login. `passwordHash` is not
   selected or changed.
6. Two correct concurrent verifications can have only one conditional claim
   winner. The loser observes consumed state after transaction conflict retry
   and receives the generic 401.

This design preserves session fixation defenses: the anonymous session that
authorized the CSRF-protected verification is deleted inside the same
transaction that creates the authenticated replacement.

## Rate limits and abuse controls

The new Express limiters use the existing trusted `request.ip` configuration
and standard bounded 429 problem response. They do not include email in a key.

| Boundary                         | Limit                                      | Additional state control                     |
| -------------------------------- | ------------------------------------------ | -------------------------------------------- |
| Existing password login/register | Existing 30 requests per 15 minutes per IP | Existing password verification behavior      |
| Existing CSRF issuance           | Existing 60 requests per 15 minutes per IP | Session rotation rules unchanged             |
| Existing reset completion        | Existing 10 requests per 15 minutes per IP | One-hour token, single use                   |
| Existing authenticated mutations | Existing 120 requests per minute per IP    | Existing authorization rules                 |
| Password-reset request           | 5 requests per 15 minutes per IP           | 60-second per-account issuance cooldown      |
| Login-code request               | 5 requests per 15 minutes per IP           | 60-second per-account issuance cooldown      |
| Login-code verification          | 20 requests per 15 minutes per IP          | 5 failures per issued code, 10-minute expiry |

Successful and failed request attempts consume the same IP buckets. Account
cooldowns return the generic 202 rather than a distinct 429, so they do not
reveal account existence. Verification returns 429 only for the IP bucket;
record exhaustion remains the generic invalid-code 401.

The existing Nginx access limiter is keyed by socket address, intentionally
shared by callers behind the local ingress. The new email request and verify
routes are not added to that 6-per-minute shared zone, because doing so would
allow one local-network caller to exhaust every learner's email-auth budget.
They remain behind the existing general API proxy and are strongly limited in
Express after the configured trusted proxy boundary resolves client IP. The
current Nginx limit for login, register, reset completion, and CSRF is not
weakened.

## Enumeration and timing model

For reset and code request issuance, public equivalence is tested across:

- HTTP status and content type;
- exact serialized body and schema;
- UI status copy;
- absence of identifiers and provider details; and
- elapsed time with the fake provider.

The implementation uses one shared response function and a 750 ms minimum
duration, with an injected monotonic clock/sleeper for deterministic tests.
Missing-account paths still perform secure random generation, keyed/digest
work, and a bounded lookup. Account cooldown is not public. Provider calls are
made only for real accounts, so an unusually slow provider can still lengthen
an existing-account request beyond the floor. That residual is documented,
rate-limited, and measured; the release does not claim perfect network-level
timing indistinguishability.

Malformed input, missing CSRF, invalid Origin, disabled capability, and IP
limit failures may return their normal distinct errors because those outcomes
are independent of account existence. Provider failures never do.

## Logging and metrics

`PilotAggregate.event` is expanded with these fixed, zero-label values:

- `password_reset_requested`
- `password_reset_email_sent`
- `password_reset_email_failed`
- `email_login_code_requested`
- `email_login_code_email_sent`
- `email_login_code_email_failed`
- `email_login_code_succeeded`
- `email_login_code_failed`

Each event is aggregated only by UTC date and event name, expires under the
existing bounded aggregate retention, and is exposed only through the existing
operator metrics command. Request events count both existing and nonexistent
email submissions; delivery events count provider attempts for real accounts.
The aggregates contain no user or request identifier and survive account
deletion because they cannot identify an account.

Logout success/failure does not add a second metric: the existing
`http.request` record already contains normalized route
`/api/v1/auth/logout`, status, and duration. This is explicitly sufficient and
avoids double-counting.

HTTP logs continue to contain only request ID, method, normalized route,
status, duration, and bounded error name. Nginx continues to log `$uri`, never
the query string. Tests fail if any captured log or metric contains an email,
API key, code, token, reset URL, cookie, CSRF value, provider response body, or
request body.

## Account export, deletion, retention, and backup

`EmailLoginCode` is transient authentication-control state, not learner data.
It is excluded entirely from `codelift.account-export.v1`; the export schema
does not change version. The defensive forbidden-key check additionally names
`code`, `codeDigest`, and `pepper`, even though no email-code query participates
in export. Tests assert that the collection and all three key names are absent
from serialized exports.

Transactional account deletion adds
`EmailLoginCode.deleteMany({ userId }, { session })` to the explicit serial
registry before user deletion. Mongo integration and Playwright cleanup/count
registries add the same model. Tests create active, expired, consumed, and
revoked records and prove that zero remain after deletion. User fencing makes
deletion and code issuance/verification mutually serializable.

No destructive migration is needed. Startup already initializes every model
idempotently with `model.init()` and `createIndexes()` while `autoIndex` is
disabled. Adding the model creates one new collection and its two indexes on a
fresh database or an existing v0.1 production-shaped database. Existing users,
password hashes, sessions, resets, invitations, progress, learning records,
and the `codelift_selfhost_mongo_data` volume are not rewritten.

The current snapshot and `mongodump` logic dynamically includes all application
collections, so encrypted backups automatically include HMAC digests and
sanitized code state but never the external pepper. Restore checks are extended
to prove that the email-code lookup and TTL indexes exist before application
startup, and the self-host fixture proves the same after startup. The isolated
restore, full fingerprint, collection count, account export, and candidate
untouched checks remain authoritative.

Before first production rollout, the operator must create and verify a fresh
encrypted backup, preserve off-device recovery evidence, record the stable
persistence fingerprint and exact volume identity, then test v0.1.1 startup
against a restored v0.1-shaped database. No `dropDatabase`, destructive schema
rewrite, `docker compose down -v`, or volume recreation is permitted.

The existing session bootstrap/state in `AccountExperience` is moved without

1. a single in-flight guard disables the button and prevents duplicate calls;
2. the provider calls the existing `logoutAccount(csrfToken)`;
3. only after the server returns 204 does it clear user, CSRF, and post-auth

4. a focused private-route request using the old cookie receives an

On any non-204/network failure, authenticated and CSRF state remain intact,
the menu stays usable, the button is re-enabled, and an adjacent focused

settings-page duplicate sign-out section is removed; there is still only one
logout API and one global UX source.

## Failure behavior

| Failure                               | Public result                   | Stored/resulting state                                        |
| ------------------------------------- | ------------------------------- | ------------------------------------------------------------- |
| Unknown reset/code-request email      | Generic 202                     | No credential and no provider call                            |
| Account cooldown                      | Generic 202                     | Existing credential remains valid; no new message             |
| Provider rejection or timeout         | Generic 202                     | Newly issued credential revoked; sanitized failed event       |
| Metrics write failure                 | Auth response is not changed    | Normal request log remains; metric loss is bounded and tested |
| Invalid/expired/revoked/consumed code | Generic 401                     | No session; active wrong-code attempt increments safely       |
| Fifth wrong code                      | Generic 401                     | Attempt becomes 5 and code is revoked atomically              |
| Concurrent valid-code verify          | One 200, one generic 401        | One authenticated session; code consumed once                 |
| Logout API/network failure            | Accessible error                | Current local authenticated state is preserved                |
| Email provider disabled               | Capability 503; email UI hidden | Password and operator recovery continue                       |
| Mongo/index startup failure           | Existing readiness failure      | API is not ready in required persistence mode                 |

## Test-first implementation strategy

Every behavior follows focused RED, minimum GREEN, neighboring regressions,
then a coherent commit. A feature implementation is not written before its
failing test is observed.

### Contract, config, provider, and content tests

- strict schemas normalize email, preserve a six-character code string, reject
  non-digits/unknown keys, and parse exact generic responses;
- configuration accepts disabled/test fake, rejects fake in production, and
  fails closed for every missing/invalid Resend field, secret path, key, pepper,
  sender, reply-to, and timeout boundary;
- code generation uses the injectable wrapper around `randomInt`, produces all
  leading-zero cases, and never uses `Math.random`;
- the keyed digest is record-bound and pepper-bound and compares in constant
  time; plain SHA-256 is not used for codes;
- email content asserts semantic subject/product/CTA-or-code/expiry/ignore copy
  using deterministic synthetic secrets in memory, without repository
  snapshots containing a secret;
- the fake captures one call and can fail deterministically with no network;
- the Resend adapter sends the expected fixed URL, headers, text/HTML, sender,
  reply-to, and idempotency key through an injected fetch;
- timeout, 4xx, 429, 5xx, malformed responses, and thrown network errors map to
  bounded errors; raw bodies and credentials are absent; and
- no provider retry occurs.

### Mongo/API tests

Password-reset request coverage proves:

- equivalent existing/missing 202 response status, headers, body, schema, copy,
  identifiers, and fake-provider timing envelope;
- one new record, one email, one-hour expiry, and prior-unused reset revocation;
- no record or email for a missing user;
- 60-second account cooldown and 5-per-15-minute IP 429;
- provider failure/timeout revokes the new record and remains generic;
- token/link/key/email absence from captured logs and metrics;
- operator reset works with provider disabled;
- reset expiry, one-time use, sibling revocation, password replacement, and
  all-session invalidation remain green.

Email-code request coverage proves:

- equivalent existing/missing response and timing properties;
- exactly six digits from secure generation, ten-minute expiry, HMAC storage,
  no plaintext in any Mongo field, and hidden digest selection;
- old active-code revocation, 60-second cooldown, serialized concurrent
  issuance, and 5-per-15-minute IP 429;
- provider called only for a real account and exactly once;
- `sentAt` gates verification; provider failure/timeout revokes and stays
  generic; and
- no code/email/provider material in logs, metrics, or export.

Email-code verification coverage proves:

- correct code returns the normal auth contract and cookie;
- wrong, unknown-email, expired, unsent, consumed, revoked, and exhausted codes
  share generic copy;
- each active mismatch increments once, attempt five revokes, and later
  attempts do not exceed five;
- one-time use and a concurrent correct verify have exactly one winner;
- success consumes the code, revokes siblings, rotates/deletes the anonymous
  session, records activity, and creates the standard session/CSRF pair;
- password hash is byte-identical and password login still succeeds;
- 20-per-15-minute verification IP 429; and
- account-deletion races cannot leave a session or login-code record.

Logout coverage retains and expands proof that the server deletes only the
current session, clears the cookie, and rejects the old cookie on a private
route. Account deletion coverage proves zero active, expired, consumed, or
revoked email-code records. Export coverage proves no email-code collection,
digest, code, or pepper is emitted.

Fresh and v0.1-shaped database tests prove idempotent collection/index creation
without data rewriting. Self-host restore tests prove the lookup and TTL
indexes survive an encrypted backup/restore before app startup and after
runtime initialization.

## Provider operator requirements and later hard stop

Resend requires an operator-owned account and a verified domain the operator
owns before arbitrary-recipient production delivery. Resend recommends a
purpose-specific subdomain for reputation isolation. The operator must choose
the domain/subdomain and region, then install the exact DKIM and SPF DNS values
Resend generates; depending on that generated configuration these are TXT plus
MX or CNAME records. A DMARC record is added after verification. No DNS value
can be safely precomputed in this repository.

The operator must also:

1. approve Resend and its data-processing/retention terms;
2. approve a sending subdomain and sender mailbox;
3. create DNS records through the existing DNS owner;
4. create a sending-access API key restricted to the selected domain;
5. save the key in an external local mode-0600 file and run the guarded
   self-host email configuration without putting the value in chat, Git,
   environment literals, command arguments, logs, or evidence;
6. allow the operator CLI to generate the independent HMAC pepper into the
   exact protected API-only path;
7. approve the plan/cost; and
8. explicitly name and approve one synthetic/operator-controlled destination
   for the first live email.

As of design research on 2026-09-12, Resend publicly lists a free plan at $0
for 3,000 emails per month with a 100-email daily limit and three domains, and
a Pro plan at $20 per month for 50,000 emails with paid overage. Pricing is an
external fact that must be reconfirmed at setup; this design authorizes no
purchase or paid-plan activation.

No live destination is authorized by the current request, so the design does
not invent one. After source, fake-provider, adapter, and release gates pass,
the implementation must stop with `EMAIL_PROVIDER_OPERATOR_SETUP_REQUIRED`
and report the account, chosen sender/domain, exact provider-generated DNS
records, exact two secret destinations, then-current cost, and the exact
operator-approved test address. The first live send occurs only after a new,
explicit approval.

## Design acceptance criteria

Approval of this design accepts these concrete choices:

- Resend behind an internal provider interface, native fetch, no SDK;
- synchronous one-attempt delivery with bounded timeout and credential
  revocation on failure;
- exact new endpoints and generic response copy above;
- one shared reset issuer and no second reset model;
- a purpose-specific `EmailLoginCode` model with `sentAt` delivery gating;
- six digits, ten minutes, five attempts, sixty-second issuance cooldown, and
  seven-day TTL retention;
- record-bound HMAC-SHA-256 with an independent 32-byte API-only pepper;
- 5/15-minute reset request, 5/15-minute code request, and 20/15-minute verify
  IP limits, without adding the new routes to the shared Nginx socket bucket;
- a 750 ms minimum generic request duration and an explicit residual-timing
  limitation;
- no login-code metadata in account export and complete transactional deletion;
- a shared React session provider for one truthful global logout control;
- fake-provider-only automated tests with a private temporary E2E outbox;
- no live email, domain, DNS, provider key, pepper, cost, or production mutation
  before its explicit operator gate; and
- the stated migration, backup, evidence, rollout, and estimated diff bounds.

Once approved, the next repository artifact is a detailed TDD implementation
plan. Production source work does not begin from this design-only stop.
